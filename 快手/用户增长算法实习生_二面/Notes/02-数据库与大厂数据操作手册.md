# 数据库与大厂数据操作手册：用户增长算法场景

> 学习路线：先明确数据粒度与口径，再写查询，最后看执行计划和数据质量。以下示例采用通用 SQL（Structured Query Language，结构化查询语言）；日期函数和分区语法需按实际引擎调整。

## 1. 最小数据模型

| 表 | 粒度 | 关键字段 | 注意 |
| --- | --- | --- | --- |
| `experiment_assignment` | 一人一实验一次分流 | `user_id, exp_id, arm, assign_time` | 先去重，分流后保留零行为用户 |
| `activity_daily` | 一人一天一产品 | `user_id, product, dt, active_flag` | 跨端总 DAU 另按用户去重 |
| `subsidy_decision` | 一次出价决策 | `request_id, user_id, dt, action, policy_version, propensity` | 记录所有候选与未补贴动作 |
| `subsidy_ledger` | 一次实际成本流水 | `request_id, cost, status, event_time` | 分清承诺、发放、核销、退款 |

DAU（Daily Active Users，日活跃用户数）是某日去重活跃用户数；MAU（Monthly Active Users，月活跃用户数）是某月去重活跃用户数。实验的分析单位应与随机化单位一致，不能把一个用户的多次事件当成独立用户。

## 2. 四道必会 SQL

### 2.1 日活与跨端去重

```sql
SELECT dt, COUNT(DISTINCT user_id) AS dau
FROM activity_daily
WHERE active_flag = 1
GROUP BY dt;
```

若主站和极速版同一用户同日均活跃，上述总 DAU 只计一次；产品 DAU 分别计数后相加可能重复。

### 2.2 次日留存

```sql
WITH cohort AS (
  SELECT DISTINCT user_id, dt AS cohort_dt
  FROM activity_daily
  WHERE active_flag = 1
), next_day AS (
  SELECT DISTINCT user_id, dt
  FROM activity_daily
  WHERE active_flag = 1
)
SELECT c.cohort_dt,
       COUNT(*) AS cohort_users,
       COUNT(n.user_id) AS retained_users,
       1.0 * COUNT(n.user_id) / NULLIF(COUNT(*), 0) AS retention_d1
FROM cohort c
LEFT JOIN next_day n
  ON c.user_id = n.user_id AND n.dt = DATEADD(day, 1, c.cohort_dt)
GROUP BY c.cohort_dt;
```

生产口径应固定 cohort 是“新增用户”还是“当日活跃用户”；`DATEADD` 是示意，不同引擎函数不同。第 7 日留存是第 7 日当天活跃，不等于 7 日内任意活跃。

### 2.3 按分流用户计算实验活跃率

```sql
WITH assigned AS (
  SELECT user_id, arm, MIN(assign_time) AS assign_time
  FROM experiment_assignment
  WHERE exp_id = 'coin_test'
  GROUP BY user_id, arm
), active AS (
  SELECT DISTINCT user_id
  FROM activity_daily
  WHERE dt = DATE '2026-11-01' AND active_flag = 1
)
SELECT a.arm, COUNT(*) AS assigned_users,
       COUNT(b.user_id) AS active_users,
       1.0 * COUNT(b.user_id) / NULLIF(COUNT(*), 0) AS active_rate
FROM assigned a
LEFT JOIN active b ON a.user_id = b.user_id
GROUP BY a.arm;
```

先检查同一用户是否进入多个组、是否在观察日前分流，再保留所有入组用户。ITT（Intention to Treat，意向治疗）按被分配策略分析，不因用户没领取金币而排除。

### 2.4 按决策统计实际核销成本

```sql
SELECT d.dt, d.action,
       COUNT(DISTINCT d.request_id) AS decisions,
       SUM(CASE WHEN l.status = 'redeemed' THEN l.cost ELSE 0 END) AS redeemed_cost
FROM subsidy_decision d
LEFT JOIN subsidy_ledger l ON d.request_id = l.request_id
GROUP BY d.dt, d.action;
```

上线前应核对流水是否一对多；退款、补发与跨日核销需明确归属日。成本可按发放、核销或净成本统计，但优化与实验必须用一致口径。

## 3. 面试常问的数据库原理

1. **索引为什么加速？** B+ 树索引通过有序键减少扫描；联合索引遵循最左前缀，过滤选择性和回表成本会影响是否使用。对高频写入表，索引增加写入与存储成本。
2. **事务与隔离？** ACID（Atomicity, Consistency, Isolation, Durability，原子性、一致性、隔离性、持久性）描述事务性质；读未提交、读已提交、可重复读、串行化依次增强隔离，具体幻读行为依赖数据库实现。金币扣减须考虑并发、幂等和重复请求。
3. **如何避免超预算并发竞争？** 预算扣减使用原子条件更新或事务中的行锁，并以 `request_id` 做幂等；若采用缓存预分配额度，需处理回收、对账和最终一致性。
4. **OLTP 与 OLAP？** OLTP（Online Transaction Processing，联机事务处理）服务实时决策与资金流水；OLAP（Online Analytical Processing，联机分析处理）服务聚合分析与实验评估。不要用分析查询阻塞在线账本。
5. **分区与执行计划？** 大表按日期或业务键分区，查询写明确时间范围以便分区裁剪；用 `EXPLAIN` 检查扫描量、Join 方式、数据倾斜与 Shuffle。先确认结果正确，再优化性能。
6. **窗口函数与去重？** `ROW_NUMBER() OVER (PARTITION BY user_id, exp_id ORDER BY assign_time)` 可取首次分流；先明确去重规则，不能用 `DISTINCT` 掩盖一对多 Join 的逻辑错误。

## 4. 大厂场景的数据质量检查

- **主键与粒度**：`request_id` 是否唯一；决策、发放和核销能否一一对应。
- **时间**：事件时间与入库时间、时区、跨日迟到数据、观察窗口是否完整。
- **实验**：SRM（Sample Ratio Mismatch，样本比例异常）、跨端分流冲突、实验互斥与埋点缺失。
- **因果日志**：propensity（倾向概率，即历史策略选中该动作的概率）是否为决策当时真实概率；未出价动作是否也有日志。
- **隐私与权限**：只访问完成任务所需的字段，避免在分析结果中暴露用户标识。
